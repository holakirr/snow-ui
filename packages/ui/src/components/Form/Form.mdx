The `Form*` parts wire a field to its label, description and error message: the ids, `aria-invalid` and `aria-describedby`. They follow the Figma Input/Form page and don't depend on a form library: pass the validation state to `FormItem`. An optional adapter for react-hook-form is a separate entry point, `@holakirr/snow-ui/react-hook-form`.

```tsx
import { Form, FormControl, FormItem, FormLabel, FormMessage, Input } from '@holakirr/snow-ui'

<Form onSubmit={handleSubmit}>
  <FormItem error={errors.email}>
    <FormLabel>Email</FormLabel>
    <FormControl>
      <Input name="email" />
    </FormControl>
    <FormMessage />
  </FormItem>
</Form>
```

The story below uses the react-hook-form adapter with a zod schema; type one character and submit to see the error.

## When to use

- Any form field that has a label, a hint or a validation message.
- With any form library (TanStack Form, Formik, Conform, server actions…), or none: pass `error` or `invalid` to `FormItem`.
- With react-hook-form, through the adapter's `FormField`.

## When not to use

- A lone field with no description or validation, such as a search field: a [Label](?path=/docs/components-label--docs), an Input `title` or an `aria-label` is enough.
- A setting that applies at once, like a [Switch](?path=/docs/components-input-switch--docs) in a settings list, doesn't need a form around it.

## Anatomy

1. **Form** (`Form`): a plain `<form>`; every prop goes to it.
2. **Item** (`FormItem`): a `<div>` that stacks its children 8px apart and gives them a shared id and the field's state: `error`, `invalid` and `name`.
3. **Label** (`FormLabel`, optional): a [Label](?path=/docs/components-label--docs) (12/16, `text-secondary`) linked to the control; `red-text` while the field is invalid.
4. **Control** (`FormControl`): a Slot around exactly one control. It gives the control the item's `id`, `aria-invalid` and an `aria-describedby` with the ids of the description and the message that are rendered.
5. **Description** (`FormDescription`, optional): a 12/16 `<p>` in `text-secondary`.
6. **Message** (`FormMessage`): a 12/16 `<p>` in `red-text`, `role="alert"` while the field is invalid. It shows `error`; without one (or with `error={true}`) it shows its children, and it renders nothing when both are empty.

The same parts without a form library: the submit handler validates the value and passes the message to `FormItem`'s `error`. The label here is Input's `title`, which works because `FormControl` gives the `<input>` the id that the title's label points at.

## States

- **Valid:** `aria-invalid="false"`; `aria-describedby` points at the description, or is left out when there is none.
- **Invalid** (a truthy `error`, or `invalid`): the `FormLabel` turns `red-text`, `FormMessage` shows the error, the control gets `aria-invalid="true"` and the message's id is added to its `aria-describedby`. `invalid` alone marks the field invalid without a message. ## react-hook-form

Install `react-hook-form` (7.60 or later) yourself: it is an optional peer dependency, and the main entry doesn't import it. The adapter exports `Form`, `FormField`, `FormItem`, `FormLabel`, `FormControl`, `FormDescription`, `FormMessage` and `useFormField`.

```tsx
import { useForm } from 'react-hook-form'
import { Input } from '@holakirr/snow-ui'
import { Form, FormControl, FormDescription, FormField, FormItem, FormLabel, FormMessage } from '@holakirr/snow-ui/react-hook-form'

const form = useForm({ defaultValues: { username: '' } })

<Form {...form}>
  <form onSubmit={form.handleSubmit(onSubmit)}>
    <FormField
      control={form.control}
      name="username"
      rules={{ required: 'Username is required' }}
      render={({ field }) => (
        <FormItem>
          <FormLabel>Username</FormLabel>
          <FormControl>
            <Input {...field} />
          </FormControl>
          <FormDescription>Your public name.</FormDescription>
          <FormMessage />
        </FormItem>
      )}
    />
  </form>
</Form>
```

- The adapter's `Form` is react-hook-form's `FormProvider`, not a `<form>`: spread `useForm()` into it and render your own `<form>` inside.
- `FormField` is react-hook-form's `Controller`. It passes the field's `name`, its error message and `invalid` to the `FormItem` inside it, so you don't pass `error` yourself.
- react-hook-form focuses the first invalid field on submit when the control gets `field.ref` (Input passes its `ref` to the `<input>`).

**Other libraries:** wrap a `FormItem` in `<FormFieldState value={{ name, error, invalid }}>` (from the main entry) to provide the state from an adapter. Props on `FormItem` win over it. `useFormField()` returns the ids and the state inside a `FormItem`, for your own parts; it throws outside one.

## Accessibility

- `FormLabel` renders a `<label for>` pointing at the control's id, so a click on it focuses the control and screen readers read it as the name.
- `aria-describedby` makes screen readers read the description, and the error while the field is invalid, after the name. It only lists the parts that are rendered, by their own `id` if you give them one, and is left out when there are none. The server HTML already has it, for the parts `FormItem` finds among its children (inside your own components they are added after hydration). `FormDescription` and `FormMessage` count wherever they render, in a portal too. Your own part with the ids of `useFormField()` counts when it is in the document as `FormItem` renders; inside the item, `FormItem` also notices it appearing, going or getting the id later (after a microtask, so wrap such a change in `await act(…)` in tests). One outside the item that changes on its own counts from the item's next render.
- While the field is invalid, `FormMessage` is an alert (`role="alert"`, WCAG technique ARIA19), so screen readers announce an error when it appears (a message on a valid field is plain text); pass `role="status"` for a polite announcement. Still move the focus to the first invalid field on submit (react-hook-form does; the story's interaction test checks it).
- The Slider passes `aria-describedby` and `aria-invalid` on to its thumbs, and the RadioGroup keeps them on its `role="radiogroup"`.
- The control must be one element that a `<label for>` can name: Input, Textarea, InputSmall, Search, a `SelectTrigger`, a Checkbox or a Switch. The RadioGroup root (a `<div>`) and the Slider root (a `<span>`) can't be: name them with `aria-labelledby` and the id of a visible label instead.

### Keyboard

The parts add no key handling: these keys are the browser's, and each control has its own (see its page).

| Key | Action |
| --- | --- |
| Tab / Shift + Tab | move to the next / previous control in DOM order; labels, descriptions and messages aren't tab stops |
| Enter | in a text field: submit the form, when it has a submit button or a single text field (the browser's implicit submission); on the submit button: submit the form. If the submit fails validation, the react-hook-form adapter moves the focus to the first invalid field (react-hook-form's `shouldFocusError`, on by default); the plain parts don't move it |
| Space | on the submit button: submit the form, as Enter does |

## Localization and RTL

- The `Form*` parts render no built-in strings: labels, descriptions and error messages are yours to translate, including the ones from a validation schema.

## Composition

`FormControl` is always a Slot: it renders its only child and merges its props into it, the child's winning for the same prop.

- Don't give the control its own `id`: it would replace the one `FormControl` sets and break the link to the label. An `aria-describedby` on `FormControl` or on the control is kept, before the description and the message.
- `FormDescription` and `FormMessage` pass their props to the `<p>`; `className` merges with their classes.

## Do and don't

<DoDont>
<Do>

- Put one control in each `FormControl`.
- Write errors that say how to fix the value: "Username must be at least 2 characters."
- Keep a `FormMessage` in every item that can be invalid.
- Use the react-hook-form entry only in apps that already use react-hook-form.

</Do>
<Dont>

- Don't set `id` on the control inside `FormControl`.
- Don't use the placeholder for instructions: use `FormDescription`.
- Don't use `FormMessage` children for hints: they show in red. Use `FormDescription`.
- Don't import `@holakirr/snow-ui/react-hook-form` without installing `react-hook-form`.

</Dont>

## Props

Each part takes the props below, `className` (merged with the part's classes) and the attributes of the element it renders. The stories render a whole form, so the tables have no controls.

### Form

A plain `<form>`: every prop goes to it (`onSubmit`, `action`, `noValidate`…).

<ArgTypes of={Form} />

### FormItem

A `<div>` that stacks the field's parts 8px apart and holds its state: `error` (a message; a truthy value marks the field invalid), `invalid` (wins over `error`) and `name`. These props win over a `FormFieldState` around the item.

<ArgTypes of={FormItem} />

### FormFieldState

A React context provider, with no props table: `value={{ name, error, invalid }}` gives the `FormItem`s inside it the field's state, the same fields as `FormItem`'s props. Adapters use it; the react-hook-form `FormField` wraps its `render` output in one.

### FormLabel

A [Label](?path=/docs/components-label--docs) whose `htmlFor` points at the control, `red-text` while the field is invalid. It takes Label's props.

<ArgTypes of={FormLabel} />

### FormControl

A Radix Slot around exactly one control: it renders the child with the item's `id`, `aria-invalid` and an `aria-describedby` that lists the rendered `FormDescription` and `FormMessage` (none when neither is rendered) after its own and the child's, and merges its own props into it.

<ArgTypes of={FormControl} />

### FormDescription

A 12/16 `<p>` in `text-secondary`, linked to the control by `aria-describedby`.

<ArgTypes of={FormDescription} />

### FormMessage

A 12/16 `<p>` in `red-text`, with `role="alert"` while the field is invalid (pass `role="status"` for a polite announcement), linked to the control while it is rendered. It shows `error`, or its children; it renders nothing when both are empty.

<ArgTypes of={FormMessage} />

### Form (react-hook-form)

The adapter's `Form` is react-hook-form's `FormProvider`, with no props table: spread `useForm()` into it (`<Form {...form}>`) and render your own `<form>` inside.

### FormField

The adapter's field: react-hook-form's [`Controller`](https://react-hook-form.com/docs/usecontroller/controller), wrapped in a `FormFieldState` that passes the field's `name`, error message and `invalid` to the `FormItem` that `render` returns.

<ArgTypes of={FormField} />

### Re-exported parts

`@holakirr/snow-ui/react-hook-form` also exports `FormItem`, `FormLabel`, `FormControl`, `FormDescription`, `FormMessage` and `useFormField`: the parts above, unchanged, so one import serves the whole form.
