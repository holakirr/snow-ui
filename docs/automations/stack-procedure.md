# SnowUI: актуальность стека

Проверяй актуальность стека проекта /Users/holakirr/Github/pets/snow-ui в этом чате раз в неделю по
понедельникам в 10:00 по Москве. Перед проверкой прочитай применимые AGENTS.md и сохранённые
результаты прошлой проверки, если они есть. Каждый раз уточняй полный состав стека по текущим
package.json всех workspace, bun.lock, CI, конфигурациям сборки, тестирования и размещения. Охвати
прямые и транзитивные зависимости, React и Next.js, TypeScript, Tailwind CSS, Radix UI, Recharts,
формы и валидацию, Storybook, Vite и tsdown, Vitest, Playwright, Biome, Changesets, shadcn registry,
Bun и Node.js, GitHub Actions и используемые контейнерные образы. Сравни фактически закреплённые
версии с последними стабильными релизами по официальным реестрам и документации; проверь официальные
security advisories, сроки поддержки и EOL, совместимость и требования к среде. Не считай prerelease
обязательным обновлением. Отличай объявленные диапазоны от версий в lockfile и реальной среды; если
среда недоступна, явно укажи это и не выдумывай результат. На первом запуске сохрани базовый снимок
в docs/stack-freshness-state.json и краткий отчёт в docs/stack-freshness.md; затем обновляй их после
проверок, сохраняя предыдущие находки и статус. Проверка выполняется без установки и обновления
зависимостей, изменения кода, lockfile, CI, инфраструктуры, публикации пакетов или деплоя. Сообщай в
этом чате при первом запуске и затем только о существенных новых изменениях: применимых уязвимостях,
прекращении или приближении конца поддержки в пределах 90 дней, важных стабильных обновлениях с
конкретной пользой или необходимых действиях. Для каждого такого пункта укажи текущую и доступную
версии, влияние на SnowUI, срочность, рекомендуемое действие и ссылку на официальный источник. Не
повторяй прежние рекомендации без изменения фактов; когда существенных изменений нет, оставайся
тихим. Недоступность источника, мешающая достоверной проверке безопасности или поддержки, считай
поводом сообщить о препятствии. Применяй humanizer-ru к своему русскому тексту.

В каждую недельную проверку включай четыре Scorecard-находки в docs/stack-freshness-state.json и
docs/stack-freshness.md: scorecard-BranchProtectionID (alert #3), scorecard-CodeReviewID (#5),
scorecard-FuzzingID (#4), scorecard-CIIBestPracticesID (#6). Через GitHub CLI/API только для чтения
получай все страницы code-scanning alerts репозитория holakirr/snow-ui, включая открытые и закрытые
состояния, и сверяй tool=Scorecard, rule ID, номер/URL, состояние, severity, сообщение причины,
последний анализ основной ветки и его commit. Номера служат исходной привязкой: учитывай повторно
открытые или заменяющие alerts того же правила. Не смешивай результаты PR/других веток с main.
Сопоставляй факты с прежними status/cause/blocker/closure_criteria/monitoring/evidence каждой
записи; обновляй отчёт и машинные статусы, сохраняя историю, дату наблюдения, ссылку и основание
изменения. Включи в monitoring этих четырёх записей явную недельную сверку Scorecard alerts этой
автоматизацией. VulnerabilitiesID/alert #7 с GHSA-vfj7-8cjw-p6xm относится к уже существующей
braces-находке: не создавай дубликат и не подменяй отдельную автоматизацию braces.

Закрывай запись только по подтверждённому устранению её причины и результату соответствующего
свежего анализа. Исчезновение alert, отсутствие доступа, skipped/incomplete analysis, смена номера
или техническое подавление не доказывают исправление; dismissal отмечай отдельно от resolved. Для
BranchProtection при изменениях читай действующие branch protection/rulesets, различай правила ветки
release и проверки её workflow. Для CodeReview не приравнивай независимое ревью агентом или зелёный
CI к человеческому approval. Для Fuzzing нужны доказательства работающей интеграции, для CII Best
Practices — подтверждённый badge. Если доступных данных недостаточно, сохраняй прежний
подтверждённый статус с явной неопределённостью.

По Scorecard сообщай только о существенном изменении относительно сохранённой базы: новом/повторно
открытом предупреждении этих правил, подтверждённом устранении причины/закрытии, изменении severity
или фактической причины/блокера, требующем другого действия пользователя. Укажи что изменилось,
подтверждение, влияние, нужное действие и прямую ссылку. Новые timestamp/analysis SHA, повтор того
же сообщения/счётчика или неизменная открытая находка сами по себе не повод уведомлять. При
недоступности источника сообщи об ошибке наблюдения один раз на новую причину; не повторяй
неизменное препятствие. Сохраняй безопасный отпечаток уже сообщённого существенного изменения/ошибки
для дедупликации без секретов и сырых логов. Если существенных изменений нет, верни DONT_NOTIFY без
комментариев вне тихого heartbeat XML. Не объявляй заново первый baseline: четыре находки уже
зарегистрированы PR #244.

Настройки защиты веток, rulesets, требования к approvals, CODEOWNERS, права доступа и правила CI без
отдельного прямого согласования пользователя НЕ меняй. Не закрывай и не dismiss GitHub alerts, не
регистрируй badge, не внедряй fuzzing и не начинай исправления в рамках этого наблюдения. Текущее
поручение разрешает сверку и обновление отчёта/реестра, а не устранение этих четырёх причин.
Сохраняй ранее согласованный read-only scope для остального стека и тишину без существенных
изменений.
