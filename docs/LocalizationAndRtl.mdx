# Localization and RTL

Every string the components render on their own — accessible names, screen-reader text, placeholders, empty states — comes from a typed `Messages` object. `SnowUIProvider` sets it (English `defaultMessages` without one), the date-fns locale for dates and the text direction. The package ships English only: translations belong to the app.

## Set up the provider

`SnowUIProvider` is a client component, and a date-fns locale and function messages are functions, which a React Server Component can't pass to a client component (Next.js App Router: "Functions cannot be passed directly to Client Components"). Put the provider in a `'use client'` module that imports the locale and the messages itself, and render it from the root layout.

```tsx
// app/providers.tsx
'use client'

import { type Messages, SnowUIProvider } from '@holakirr/snow-ui'
import type { ReactNode } from 'react'
import { ru } from 'react-day-picker/locale' // a date-fns locale plus day-picker labels

// Module scope: the same object on every render.
const messages: Messages = {
  /* alert, alertDialog, avatarGroup, badge, breadcrumb, calendar, charts,
     combobox, commandPalette, datePicker, dialog, dropdownMenu, input,
     link, listCards, pagination, progress, search, sheet, sidebar,
     slider, spinner, tag, textarea, toast */
}

export const Providers = ({ children }: { children: ReactNode }) => (
  <SnowUIProvider messages={messages} locale={ru}>
    {children}
  </SnowUIProvider>
)
```

```tsx
// app/layout.tsx (a Server Component)
import { Providers } from './providers'

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="ru">
      <body>
        <Providers>{children}</Providers>
      </body>
    </html>
  )
}
```

For several languages, pass the language (a string) from the layout and pick the locale and the messages inside `Providers`: `<Providers lang={lang}>` with `const { locale, messages } = translations[lang]`.

## Messages

- **Typed and grouped by component:** `messages.pagination.previous`, `messages.dialog.close`… The namespaces are `alert`, `alertDialog`, `avatarGroup`, `badge`, `breadcrumb`, `calendar`, `charts` (the `@holakirr/snow-ui-charts` package), `combobox`, `commandPalette`, `datePicker`, `dialog`, `dropdownMenu`, `input`, `link`, `listCards`, `pagination`, `progress`, `search`, `sheet`, `sidebar`, `slider`, `spinner`, `tag`, `textarea` and `toast`.
- **Functions for values:** strings with values are functions, so a translation can order and inflect them: ``tag: { remove: (label) => `Удалить тег ${label}` }``, `calendar: { previousYears: (count) => … }`.
- **Partial:** `messages` takes any subset (`MessagesOverrides`) and merges it over the defaults, namespace by namespace; a message set to `undefined` keeps the default. Providers nest: an inner one overrides the outer one for its subtree.
- **Stable:** define `messages` at module scope (or `useMemo` it). Inline function messages are new functions on every render, which re-renders every component that reads the messages.
- **Component props win** over the provider: `closeLabel` (`DialogHeader`, `SheetContent`), `clearLabel` and `placeholder` (`Search`), `clearLabel` / `statusLabel` (`Input`), `removeLabel` (`Tag`), `externalLabel` (`Link`), `label` (`BreadcrumbEllipsis`, `PaginationEllipsis`), `label` / `placeholder` / `emptyMessage` / `loadingLabel` (`CommandPalette`), `label` / `placeholder` / `emptyMessage` in `search` (`DropdownMenuContent`), `emptyMessage` / `loadingLabel` / `clearLabel` / `createLabel` (`Combobox`, `MultiSelect`), `placeholder` / `clearLabel` (`DatePicker`, `DateRangePicker`), `thumbLabels` / `valueFormatter` (`Slider`), `todayLabel` / `lastSelectionLabel` / `labels` (`Calendar`), `statusLabel` / `dismissLabel` (`Alert`), the children or `label` of `AlertDialogCancel`, `getValueLabel` (`Progress`, `ProgressCircle`), `label` (`Spinner`), `title` (`NotificationsCard`, `ActivitiesCard`, `ContactsCard`) and `aria-label` (`Breadcrumb`, `Pagination`, the previous / next links, `ToastClose`, `SidebarTrigger`, `Badge`, `Progress`, `ProgressCircle`).
- **Your components:** `useMessages()` returns the current messages; `useSnowUI()` returns the messages, the `locale` and the `dir`.

## Dates

- `locale` goes to `Calendar` (month and weekday names, day labels; its own `locale` prop wins), to the dates `DatePicker` and `DateRangePicker` show and to `Scheduler`'s day, time and cell labels (`locale.code`; `en-US` without a locale, so the server and the browser render the same text).
- The first day of the week in `Calendar`, `DatePicker`, `DateRangePicker` and `Scheduler` is Monday, as in the Figma kit, whatever the locale. `SnowUIProvider`'s `weekStartsOn` changes it for the subtree: a day (`0` for Sunday … `6`), or `"locale"` for the locale's first day (`locale.options.weekStartsOn`: Sunday with the default `enUS`, Monday with `ru`). Their own `weekStartsOn` prop (`startOfWeek` on `Scheduler`) wins. 6.0 makes `"locale"` the default.
- A react-day-picker locale (`react-day-picker/locale`) also translates the day picker's own labels (day buttons, dropdowns…).
- `messages.calendar.previousMonth`, `nextMonth` and `navigation` name the month navigation, so it translates with a plain date-fns locale too. Their English defaults give way to a react-day-picker locale's labels; a translated message wins over those, and `Calendar`'s `labels` prop over both.

## Right-to-left text

Set the direction on the document and on the provider:

```tsx
// app/providers.tsx
'use client'

import { SnowUIProvider } from '@holakirr/snow-ui'
import type { ReactNode } from 'react'
import { ar } from 'react-day-picker/locale'
import { arMessages } from './messages'

export const Providers = ({ children }: { children: ReactNode }) => (
  <SnowUIProvider dir="rtl" locale={ar} messages={arMessages}>
    {children}
  </SnowUIProvider>
)
```

```tsx
// app/layout.tsx: only strings cross into the client.
<html lang="ar" dir="rtl">
  <body>
    <Providers>{children}</Providers>
  </body>
</html>
```

- **Layout** follows the DOM `dir`. The components use logical utilities (`ps-` / `pe-`, `ms-` / `me-`, `start-` / `end-`, `text-start`, `rounded-s-` / `rounded-e-`, `border-s` / `border-e`), so paddings, icons, check marks, badges, a `Tag`'s remove button and the rounded ends of a `Calendar` range swap sides. `dir` on any element scopes it to a subtree, like `data-theme`. Use the same logical utilities in your own layout.
- **Directional icons** point the other way: the pagination and calendar arrows, the `Accordion`, menu and submenu arrows, the `Link` arrow and external icon, `SidebarTrigger` and icon separators of `BreadcrumbSeparator` get `rtl:-scale-x-100`. For your own icons use the same class (or the icons' `mirrored` prop). `Switch` moves its thumb the other way.
- **Keyboard** follows the provider's `dir` (it wraps Radix's `DirectionProvider`): in `Tabs`, `RadioGroup`, `ToggleGroup`, `Slider` and a horizontal `Accordion` ArrowLeft moves forward, menus open submenus to the left with ArrowLeft, and `Calendar` passes `dir` to react-day-picker's arrow keys.
- **Portals** (`Dialog`, `AlertDialog`, `Sheet`, `Popover`, `DropdownMenu`, `ContextMenu`, `Tooltip`, `Select`, `CommandPalette`, the lists of `Combobox` and `MultiSelect`, the calendars of `DatePicker` and `DateRangePicker`, the toast viewport) render outside your `dir` scope, so they take `dir` from the provider.
- **Sides:** `Sheet` and `Sidebar` take `side="start"` / `"end"` (defaults: `Sheet` `end`, `Sidebar` `start`), resolved with the provider's `dir`; `left` / `right` stay physical. `Tag`'s `arrow-start` / `arrow-end` shapes flip, `arrow-left` / `arrow-right` don't. `Typography`'s `align` takes `start` (the default) and `end`. In right-to-left text toasts are swiped away to the left.
- **Keyboard shortcuts** (`KBD`) always read left to right.
